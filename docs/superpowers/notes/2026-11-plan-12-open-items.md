# Plan 12 (Care updates: a weekly WordPress update batch run by the Mac helper): open items after the build

Branch `feat/agency-os-care-updates`, built 2026-11-21 by subagents: the implementers and the task reviewers on Sonnet. One migration, `0062_care_updates`. The helper is now version `0.2.0` (the server's `MIN_HELPER_VERSION` stays `0.1.0`, so an old helper never takes a Care job and keeps doing voice and render). **Nothing is deployed, pushed, merged or migrated remotely. No page was ever opened in a browser. No real SSH, WP-CLI, Chrome, ffmpeg or TLS call was ever made**: every one of them is a fake in a test (a recorder for `ssh` and Chrome, fake JPEG bytes, a fake certificate socket). The first real run is yours (Needs Logan, items 4 to 6).

What was built, in six parts.

The weekly batch. On CARE-1's weekday (Wednesday, booking zone) the daily cron starts one batch for the week and queues one read-only `care.inventory` job per site that can take updates: real, live, WordPress, access method SSH with WP-CLI, an alias and a folder set, a client with live Care and no billing hold. MainWP sites, test clients and clients without Care are left out. The helper reads each site (five WP-CLI reads) and reports its versions and every update waiting. Each update gets a risk from version numbers alone (security is a tick you set by hand), and a major waits 7 days from the day the app first saw it. Sites are grouped (WooCommerce, booking, builder, brochure) and the canary of each group is its cheapest Care plan, then domain. When the last inventory is in, wave 1 is drafted: ONE approval (`care.updates`) that names the canaries and their due updates. After the canary runs and its changed pages are looked at, wave 2 is drafted for everyone else. A rejected wave 1 cancels the batch. A daily backstop drafts a wave a lost hook missed, drops a run that never got a job and cancels a weekly batch made more than six days ago, in any wave and whether or not CARE-1 is on, rejecting its pending wave approvals (R41).

The update run. Only an approved wave queues a `care.update` job; at approval everything is read again and only what still applies is queued, at the version the site now shows, and what was dropped is said in the run's summary. The helper takes a backup (`wp db export`, gzipped into `siteline-backups/` in the SSH user's home, kept 28 days), shoots the pages (headless Chrome, up to five per site), applies the updates one at a time, re-reads each version, shoots the pages again and compares them (ffmpeg SSIM; under 0.95 is "changed"). A page that now returns 5xx (or 404 or 410 where it was fine), shows the critical-error text or has fewer forms is "broken": the helper puts the old code back (`wp plugin install <slug> --version=<from> --force`, the same for themes and core) and **never imports the database**. A retried job never applies an update. Every value that reaches the remote shell is checked against a fixed pattern on both the Worker and the helper, and `ssh` is started with an argument list and `BatchMode`. So a cache in front of the site (WP Rocket, the host's Varnish, Cloudflare) cannot answer with a copy from before the update, every page read and screenshot asks for its own address (`?siteline-check=<run id>-<attempt>-<page>-<before|after|recheck>`, R40), every read sends `cache-control: no-cache` and `pragma: no-cache`, and `wp cache flush` runs after the updates (R20).

Looking at changed pages. A changed page waits for Claude: a `care.review` task with the three pictures (before, after, difference) in the untrusted block; Claude answers fine, broken or unsure with a short note. `fine` lets wave 2 go. `broken` or `unsure` opens an incident and holds that group out of wave 2 for the week. Your own "Looks fine" overrides Claude's look.

Incidents, tasks and the board. A rolled-back or failed run opens one `update_failed` incident (a fixed sentence such as "updates rolled back: x broke /contact", never text from a site) and one CARE-5 fix task on the client's live Care project. The incident stays open until **you** close it (`POST /api/incidents/:id/close`): no run closes it, a later failure on the site replaces its sentence with the newer one when that one ranks the same or higher (a restore instruction is never replaced by a milder sentence, R39), and while it is open the site sits out the weekly batch (a single-site run may still take it). A weekly batch ticks each client's CARE-1 checklist as it moves (1.1 and 1.2 when planned, 1.3 once a canary ran, 1.4 when you approve, 1.5 and 1.6 once the batch settles and nothing of the client failed); a rolled-back client keeps 1.6 open for you. The helper also reads each monitored site's TLS certificate expiry once a day (`care.certs`); 14 days or less opens a `cert_expiring` incident. Health takes 15 off for each open `update_failed` and `cert_expiring`. Today shows an update failure at priority 85, a page waiting on a look at 70 and a certificate at 66.

Routes, MCP and pages. `GET /api/care/updates` (the board), `PUT /api/care/updates/:id` (hold an update, or call it security), `POST /api/care/batches` (start this week's batch now), `POST /api/sites/:id/care-run` (a single-site run, a rehearsal site included), `GET /api/care/runs/:id`, `GET /api/care/pictures/:checkId/:kind`, `POST /api/care/checks/:id/ok` (Looks fine) and `POST /api/incidents/:id/close`. The `agency-os` MCP server now has 28 tools: the read-only `get_care_updates` shows each site's domain, whether it can take updates (and why not), its updates by slug and version with risk, and its last run, and never a plugin name, an alias, a folder, a page body or a picture. The pages: `/care/updates` (the board), a run view (`/care/runs/:id`: the backup file name, each page with its pictures and look) and a Care updates block on the client's Care panel with the single-site button. The site panel has the alias, the folder and the pages to check.

End-to-end test. `test/care-updates-flow.test.ts` drives the real entry points on a fixed calendar (Los Angeles, Wednesday 2 December 2026, 09:00): the daily cron, the Mac helper's own routes under `/helper` with a real device token (claim, upload to the exact keys of the job, touch, complete), the owner's routes under `/api`, the real approval path, the queue's real completion for Claude's look, and the MCP route. The only fakes are the registry lookup the daily cron makes (a recorder that answers nothing) and the mail transport, which must see nothing; the helper is played by the test. The story: three Care clients with brochure sites (one the cheapest), a Care client on MainWP, a test client with a test site and a client without Care. The cron queues exactly three inventories and one certificate read. Completing them drafts one wave-1 approval naming only the cheapest site and only its small update (a major seen that day is in no wave). Approving it queues one job whose payload carries the alias and the folder and nothing else secret (no vault name, access note or token). The canary completes with one changed page, a `care.review` task appears and wave 2 is not drafted. Claude's `fine` through the queue's completion drafts wave 2 for the other two sites. Approved, one site completes clean and one rolls back (plugin `x`, `/contact` returns 500): one `update_failed` incident, one CARE-5 task, a Today row at priority 85, health 15 lower (85), `care_rolled_back` on the timeline, the clean clients' CARE-1 tasks done and the rolled-back one with 1.6 open. At the end the approvals are exactly the three wave approvals and the single-site one, no mail was sent, no error was logged, and no MCP answer or `/api` body contains an alias, a folder, a picture key, a vault name, an access note or a token. ## Decisions for Logan

The fifteen calls the plan made:

1. Only `ssh_wpcli` WordPress sites with an alias and a folder are updated. MainWP and "none" sites are listed on the Care page as "can't update: no SSH access" and nothing more. NEEDS YOUR CALL.
2. The helper runs `ssh -o BatchMode=yes <alias> -- wp --path='<folder>' ... `. The alias is a `Host` entry in your `~/.ssh/config` with a 1Password or ssh-agent key; the app stores the alias name only.
3. The batch day is CARE-1's day (Wednesday, editable in Settings). The daily cron on that day queues an inventory of every updatable site; when the last one is in, wave 1 is drafted.
4. Risk classes come from version numbers alone: core major is a change in the first or second number, plugin or theme major a change in the first, mild the second, minor the rest; a version that can't be read is major. There is no vulnerability feed (the free ones need sign-up and have limits), so **security** is a tick you set by hand, which skips the wait. NEEDS YOUR CALL.
5. A major waits 7 days from the day the app first saw it (WP-CLI does not report the release date). NEEDS YOUR CALL.
6. A tick from you is needed even after the canary passed for: every major, core, any update that can't be rolled back, and anything whose slug matches `RISKY_SLUGS` (WooCommerce and its extensions, Elementor, Beaver Builder, Divi, WPBakery, Gravity Forms, WPForms, Contact Form 7, Ninja Forms, Formidable, Amelia, Bookly, any slug with `booking`). The list is one constant. NEEDS YOUR CALL.
7. Groups come from the installed plugins: `woocommerce`, `booking`, `builder`, else `brochure`. One canary per group, two when a group has six or more sites, lowest Care price first, then domain; a single-site run has no canary.
8. Forms are counted, never submitted: a page that had N `<form>` elements and now has fewer is broken. Submitting a client's real form would email the client; a real delivery test stays a hand check.
9. No staging copy, Care Plus included ("big changes use staging" is not met). Instead: canaries, your tick on big changes, a database backup and automatic code rollback. Staging is host-specific; say if you want it for Care Plus in a later plan. NEEDS YOUR CALL.
10. The backup is `wp db export` on the server into `siteline-backups/<domain>-<run id>.sql.gz` under the SSH user's home, kept 28 days; files are left to the host's own backups. The automatic rollback puts old code back and **never** imports the database (it would lose orders and form entries made since); the incident names the backup file for you to restore by hand. NEEDS YOUR CALL.
11. A page is **broken** after updates on: status 5xx, 404 or 410 where it was 2xx before, the "There has been a critical error" text, a WP-CLI error, or fewer forms. Broken rolls the site back by itself. A page is **changed** when the screenshot's SSIM is below 0.95: no rollback, Claude looks (fine, broken or unsure); broken or unsure becomes yours. NEEDS YOUR CALL.
12. Up to five check pages per site (`care_paths`, default `/`), desktop width 1280, height 1600, first screen only.
13. Certificate expiry is read daily by the helper for every monitored site; 14 days or less (or expired) opens a `cert_expiring` incident, which closes when a later read is over 14 days. If the Mac is off, the last reading stands. **Not built:** the plan said "the board says how old it is"; no page shows the reading's age (see the known gaps).
14. Health: an open `update_failed` takes 15 points and a `cert_expiring` 15. Today: `update_failed` at priority 85, `cert_expiring` 66, a page waiting on your look 70. NEEDS YOUR CALL.
15. Cut line (spec section 12, six-week rule), not used: nothing was dropped. If the branch had to shrink, certificates (Task 10) were to go first, then the Claude look (Task 9: a changed page becomes yours directly), then the pages (Task 12), keeping the routes.

The rulings made while building (each is plain: what, and what it costs):

- R1. `src/worker/care/args.ts` (the fixed patterns and `SshTarget`) was made in Task 1, not Task 3, because the site route's checks needed it first. Costs nothing.
- R2. The helper has its own `Verdict` type (`ok`, `changed`, `broken`) because it can't import from the Worker; a drift between the two is caught by the flow test's results. The SSIM 0.95 cut is likewise written once in each package.
- R3. A rehearsal client has only a test Care subscription, so `updatableSites` with `includeTest` also accepts a test client's test subscription. The weekly batch never includes a test site. Costs: a test site can only slip into a single-site run.
- R4. `care_updates.risk` always holds the version-based class; your security tick lives only in the separate `security` flag. Else a security-ticked major would skip your tick.
- R5. `wp core version` is run without `--format` (the plan's `--format=json` is not valid WP-CLI) and read as text; a "no update" answer is accepted only on the exact line `Success: WordPress is at the latest version.`; anything else is an error. Costs a helper change if WP-CLI prints something else on the real server.
- R6. Slugs may be upper case (`^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`) on both sides, because theme folders such as `Divi` are real. Still no shell character. The inventory result gains `dropped` (rows the helper refused or cut at 300 plugins and 50 themes); the Worker logs a warning.
- R7. After each update the helper re-reads that component's version; "applied" only when it reads the target. A failed attempt that left the version changed (or unreadable) counts as half-installed and the site is rolled back. Costs one more WP-CLI call per update.
- R8. A retried job (claimed more than once) never applies an update: it reads versions, reports what is at the target version, runs the page checks with absolute rules (no before-shot to trust; forms are ignored) and rolls back if a page is broken. The result carries `retry: true`. Costs: an interrupted week's updates wait for the next batch.
- R9. Contact guard: once the helper's last successful keep-alive is older than 10 minutes it starts no new update ("stopped: lost contact with Agency OS") but may still check pages and put code back.
- R10. A page's status is kept once headers arrive; a body that stalls or throws counts as an empty body, not as "no answer", else a slow page would trigger a false rollback. A screenshot counts only if the file was written.
- R11. Run status: `rolled_back` if the helper put code back; else `failed` if a step failed, a page is broken with nothing put back or the backup failed; else `changed` if a page changed; else `ok` if something was applied; else `dropped` with the helper's reasons. Every `failed` and `rolled_back` opens `update_failed`; a job the helper gave up on also does ("update failed on the Mac helper"), because it may have half-updated a site. A client without a live Care project gets the incident but no fix task. ~~The incident closes only on an `ok` run.~~ Corrected by R26: no run closes it; only you do.
- R12. `onInventoryDone` and `onRunDone` can be called any number of times. An empty wave 1 goes straight to wave 2; nothing due at all makes the batch done. A group whose canary runs were all dropped is held out of wave 2 for the week and the preview says so.
- R13. A single-site run ticks no CARE-1 item (it is a baseline or a rehearsal, not the weekly cycle). 1.5, 1.6 and completing the task wait until the batch has settled. A checklist is ticked only if it lines up with the template (same length, each item starting with the step's title). A tick error is logged and swallowed, never breaking the batch.
- R14. (Found by the flow test) The last inventory never drafted wave 1 on the real helper route. `completeHelperJob` runs the kind's `apply` while the job is still `claimed`, and `onInventoryDone` counted that job as open. The unit tests marked the jobs done first, so they never saw it. Fixed: `apply` passes its own site id and `onInventoryDone` leaves that one job out (`src/worker/care/inventoryKind.ts`, `src/worker/care/batch.ts`), with a test that completes two jobs through `completeHelperJob` (`test/care-batch.test.ts`). Without the fix the batch would have waited for the backstop at the next daily cron, a day late. Costs nothing.
- R15. (Found by the flow test) A wave-2 client's CARE-1 checklist never finished: step 1.3 ("test sites updated and checks pass") was ticked only for the clients that had a canary run, so every other client's task stayed open for ever. Fixed: once a canary run of the batch has ended, 1.3 is ticked for every client that has a run (`src/worker/care/tasks.ts`), with a test in `test/care-tasks.test.ts`. A client with no run in the batch (nothing due for it) is still not ticked; see the known gaps.
- R16. A canary page whose look ends `broken` or `unsure` means the canary did not pass: that group is held out of wave 2 for the week, and the preview says "waits until next week: a page on the <group> canary looked different". Your "Looks fine" accepts a pending, unsure or broken look (it overrides Claude's), marks it `logan_ok`, and releases the group; the incident stays open for you to close. A changed page with a missing picture is `unsure` with an incident.
- R17. `get_care_updates` drops the plugin name and shows a slug, a "from" or a "to" only if it matches the fixed patterns; others are only counted (`skippedUpdates`). An incident's detail is built from checked slugs, a checked page path and fixed sentences, and re-checked on the way out.
- R18. The check-path pattern refuses `//` at the start in both packages (`//evil.com` is not a path). An attempt to put `//evil.com` into the shared hostile tables was dropped because the alias and folder patterns reject it for other reasons; the direct assertions on both sides are the pin.

The rulings of the whole-branch review fix wave (2026-11-21). Each says what changed and what it costs.

- R20. (C1, page caching) Every page read and screenshot carries its own `siteline-check=<run id>-<page index>-<before|after|recheck>` query (since R40 `<run id>-<attempt>-<page index>-<before|after|recheck>`) (added after `pageUrl`'s same-origin check, `&` when the path already has a query), every read sends `cache-control: no-cache` and `pragma: no-cache`, and after the updates and before the after-shots the helper runs `wp cache flush` (best effort: a failure is ignored). Before this a failed update vanished from every wave for good. Costs: an update that broke once is offered again each week until you hold it.

Costs: you must close each incident by hand before the site is in a weekly batch again.

Costs: on a retry (no before-read to compare with) a check page that was already a 404 before the update also reads "still broken" after a rollback; on a first attempt R38 fixes this.

(G1, the culprit came back unstamped) When the helper puts back an update whose own step failed (its version moved, so it is in the put-back set), that step keeps its own identity: outcome `rolled_back` with the new fixed note "put back after this update failed" (or `rollback_failed`, see below), whether or not a page broke. (G5, the week window and the batch that never ended) The stale-approval check keys on the batch's age, not the ISO week: execute refuses a weekly batch made more than six days ago (and one that is done or cancelled), so a batch started on a Saturday can have its wave 2 approved on Monday. The daily backstop cancels any unsettled weekly batch made more than six days ago, in any wave (not only while reading its sites) and whether or not CARE-1 is on, expires its open inventory jobs and rejects its pending `care.updates` approvals with the note "this week's batch ran out of time"; runs already queued are left to finish. A new week's batch still rejects earlier weeks' pending waves (R22). Both rejections go through the shared `reject` of `approvals/decide.ts` (status, `decided_at`, `decision_note`, `error` cleared), as your own reject does. Costs: a wave you meant to approve on day seven is gone; the next batch plans it again.

## Known gaps (decided, not fixed)

Never run for real
- Nothing here has met a real server. The assumptions most likely to be wrong on the first real run: the exact text of WP-CLI answers (`core check-update`, `plugin list --fields=...`, the `Success:` line), `wp db export` and `gzip` paths in a restricted shell (the helper uses paths relative to the SSH user's home), `find -mtime` on the host, headless Chrome flags (`--headless=new`, `--virtual-time-budget`), the ffmpeg SSIM line, the cost of 500 certificate hosts in 20 minutes (about 18) and the 20-minute claim for a very large batch.
- The helper's own tests use a recorder for `ssh`, Chrome and ffmpeg.
- The three screenshots only show the first screen at 1280 wide; a problem lower on the page, or on mobile, is not seen.

Batch and tasks
- No page shows how old a site's certificate reading is (decision 13 said the board would); a Mac that has been off for days shows the last date without saying so.
- 1.4 is ticked even when every site of an approval was dropped; a client whose runs were all dropped gets 1.5 and 1.6. A client with no run in the batch (nothing due) gets no tick at all and its CARE-1 task stays open for you to close.
- `tickPlanned` uses the sites known at draft time; a checklist edited in the template after a task was made is skipped by design.
- Pressing "Looks fine" after a batch has settled does not draft a late wave 2; the group waits a week.
- `startSingleRun` checks for an open run and then inserts, so two clicks in the same instant could both pass (a partial unique index would close it); a single-site run ignores an open weekly inventory or pending wave of the same site.
- A rejected wave 1 cancels the batch (not in the plan; it keeps the rest from going without a canary).
- A group with due sites and no canary row would skip the canary (the canary pick prevents it today).

Helper
- A retry leaves a component whose version cannot be read unrolled; the retry note for a hand-changed component reads awkwardly; `cli info` shows the CLI's PHP, not the web server's.
- No limit on the length of a string before it is trimmed; `activeTheme` is not slug-checked; a trailing notice after `wp core version` fails closed.
- The certificate deny-list is narrower than the Worker's list of internal suffixes; the destroy and hard-timer paths are untested; there is no timeline line for certificate incidents.
- `wp cache flush` empties only WordPress's object cache; a page cache plugin's own files or a CDN are not purged (the cache-busting query and the no-cache headers are what get past them).
- `pageUrl` is not tested with `@ ? # %2F` or a backslash; `/<form/` also matches `<formal`.

Worker and routes
- `get_care_updates` has no cap on the number of sites; `careUpdatesBoard` reads each site's inventory one at a time; `PUT /care/updates/:id` also works on rows that are no longer `available`.
- A dropped run is told apart from an expired one by its summary text; a late result after `onFail` is accepted silently; unknown step ids in a result are ignored; a very long slug list falls back to the generic incident sentence; the CARE-5 key is written twice (`sops.ts` and `incidents.ts`).
- The header comment of `care.ts` should say that the incident text is built only from checked values.

Pages
- Never opened in a browser (see Needs Logan). Known rough edges: `aria-disabled` buttons have no visual cue; "Plan updates" is live on a site that cannot take updates (the server refuses it with a sentence); the Care panel shows "No update run yet" when the read failed; the run page shows more than the latest run; a held security badge is red; some picture alt text is terse; the zone can flash on first render. A test client's runs and incidents are linked from no page (the updates board, Today and the incident lists leave test clients out), so a rehearsal's run view is opened by its URL and its incident closed by the API (Needs Logan, item 5).

Tests
- The same known flakes as before, each passing alone: `billing-flow`, `billing-sweep`, `projects-flow` (timing under full-suite load), the MCP rate-limit test when it runs beside other MCP tests, and `sites-onboarding-items` (fails when a random UUID contains "abc").
- The flow test pins only `Date`, so real timers are real; every fake answer is immediate, so none fires. It plays the helper through the real routes, but the helper's own code never runs in it: the results it sends are written by hand to the shapes in `inventoryKind.ts`, `updateKind.ts` and `certsKind.ts`, so a change in what the helper really sends is caught only by the Worker's result schemas.

## Rollback
The Worker can be rolled back safely onto the new schema: the old code ignores the new columns and tables, and the rebuilt `site_incidents` keeps every Plan 11 row. The schema itself is rolled back only through the D1 Time Travel bookmark recorded before migrating (Needs Logan, item 1). Rolling back the helper to `0.1.0` is also safe: it does not claim Care jobs, so any open Care jobs simply expire after 14 days and the batch's backstop cancels what is left.
