# Plan 14 (Local SEO: profile, rank grid, review watch, content drafts, monthly report): open items after the build

Branch `feat/agency-os-local-seo`, built 2026-11-21 by subagents: the implementers and the task reviewers on Sonnet. One migration, `0064_local_seo`, which comes after `0061_monitoring`, `0062_care_updates` and `0063_care_reports` (if those three are not yet deployed, this build carries their code too). The `agency-os` MCP server now has **30 tools** (it had 29). **Nothing was deployed, pushed, merged or migrated by this build; what is applied remotely is for you to check with `wrangler d1 migrations list`.**

**What was never run for real.** No real Google Places call was ever made: every test answers `fetch` with a small fake that knows the shapes of a text search, a place's details and an ids-only search, and I wrote those shapes from Google's documentation, so a field the real answer names differently shows up on the first real run. No real mail was sent (the mail transport is a fake in every test). No page was ever viewed against the real Worker: the owner pages (the client's Local SEO panel and `/seo`) and the client's report page (`/l/<token>`) were looked at only on a local rig by their implementers, at desktop width and at the 375 phone preset. No client has a real report. The rank number is an approximation, not what Google Maps shows any one person: it is the position of the listing in the first 20 results of a Places text search for the term, with the search biased to nine points around the business. A phone in the same spot may see a different order (Maps uses the person's history and device), and Places returns up to 20 results where Maps keeps loading more. Every page and mail says "in our check" and the report never promises a position, but the grid is an indicator, not a measurement of Maps. Google Business Profile's own numbers (calls, directions, clicks, searches) are not read at all: they need the Business Profile API, which Google approves by request. The first real run is yours (Needs Logan below).

What was built, in seven parts.

The setup. A client's Local SEO profile is tied to ONE Google place that you pick from a search (`POST /api/clients/:id/seo/place-search` shows up to five businesses and picks none, even when two share a name). The place's location, name, address and phone always come from Google, never from what you type. You also give the trade, up to eight towns and the grid spacing (1 to 10 km, default 3). Up to ten search terms ("keywords") can be active, each with an optional town; twelve citation directories are listed for you to mark by hand (to do, listed, needs fixing, not applicable). The name, address and phone check reads the client's home page and the contact page it links to and compares them with Google's details (match, mismatch or missing for each). When the listing has nothing to compare with (no phone, a service-area address with no street number, no name) that part is `unknown`: the owner's panel and Claude's brief say "not compared", and the client's summary and page never mention it. The baseline button (`POST /api/clients/:id/seo/baseline`) saves the listing's numbers, runs that check and the first rank grid, and switches the watch on. SEO-0 to SEO-3 are four new seeded checklists. SEO-0 (nine steps, a project of kind `custom`) is started by a signed, paid Local SEO document the way the build is; finishing its last step attaches SEO-1 (monthly, due the 10th), SEO-2 (quarterly) and SEO-3 (annual).

The rank grid. For each active keyword the app makes nine ids-only Places searches, one from each point of a 3 by 3 grid centred on the business (the search circle around each point has half the grid spacing as its radius, so neighbouring circles meet), and stores, for each point, the position of the listing on page one (1 to 20), "not in the top 20" (a real answer) or "not checked" (the call failed; never shown as "not ranking"). A check counts only when at least 7 of its 9 points were measured. One check per keyword per local day; a second run the same day replaces the first, but a point that failed the second time keeps the first run's reading from the same spot.

The daily sweep (`sweepSeo`, the last part of the daily cron, after the Care reports). For each real client with an `active` profile, no billing hold and a live project carrying SEO-1, at most 25 clients a run, the one handled longest ago first: (1) it reads the listing again when the last read is more than 6 days old (so in practice every 7th day): saves the day's snapshot (rating, review count, photo count, hours flag, category), stores any new reviews Google shows (at most five, not necessarily the newest) once each, and queues ONE Claude task for the new ones; (2) it pulls the month's ranks when no check was taken today, some active keyword has no usable check this month, and fewer than four days of the month have had a pull (so a throttled first day is retried on later days at a bounded cost); (3) with no Places call at all: it makes the month's content slots once the month has any check, ticks SEO-1's step 1.1 once a usable check exists, and starts last month's report once a usable check from after that month exists. Places work stops for the whole run, with one logged line, when the places sub-cap or the total cap is reached, and the run stops starting any client's Places work after 400 calls or 6 minutes after it began, whichever comes first (reports, slots and ticks are never held by either; the clients not reached wait for the next run and go first in it). The limits, as I found them: a scheduled Worker on the Paid plan may make 10,000 subrequests an invocation, every D1 call counts as one and a Places call is two (the request and the row that records its price), so the subrequest limit is not what binds a run; the wall time is (about 15 minutes for a scheduled run, with the Places calls made one after another), hence the 6 minutes of Places work and the 400 calls (four clients with ten terms). A client whose Google place has gone or changed is paused by the watch: when Google answers 404 for the stored place id, or answers with a different id, the profile goes to `paused`, ONE timeline line says so ("Local SEO paused: Google no longer knows this place: pick it again", or "... lists this place under a different id ...", no place text in it), the watch day is set so the paid call does not repeat every day, and that client gets nothing else that day or after (no pull, no report). Picking the place again (`PUT .../seo/profile`) and pressing the baseline switches the watch back on. A rank run stops at the first 401 or 403 (a key Google refuses) instead of firing all its calls; the day's check is stored as not checked, so the client is not tried again that day. A test client, a client on billing hold, a profile in `setup` or `paused` and a client with no live SEO-1 cadence get nothing.

Reviews. A new review of 3 stars or fewer is flagged. Claude writes a reply to each new review (one task for up to ten): review text, reviewer names and the business name go only in the untrusted block; a reply with a link, an email address, a phone number, a dollar amount, an offer (refund, compensation, free work, free estimate or quote, complimentary, no charge, discount, guarantee; "feel free to call us" is fine), markdown or a run of blank lines is refused and the task stays claimed. The app never posts anywhere: you edit the draft (same text rules), paste it in Google and press "posted". Today shows a row for each client with drafts waiting (priority 58) or a low-rated review that still needs you (66).

Content. Each month a Local SEO plan gets 2 pieces (a service or location page, then an answer-style post) and 1 Google Business Profile post; Growth gets 4 and 2. Each slot takes the active keyword with the fewest pieces so far (over all months), and a Claude task writes the draft (title, meta title up to 60, meta description up to 160, body up to 12 000 characters, a Google post up to 1 500 with no meta text; no script, phone number, email, dollar amount or ranking promise). You edit, approve, and mark it published (with the address, https) after you put it on the client's site or profile yourself. The app publishes nothing.

The monthly report. Per client, for the previous calendar month in the booking zone: the grid per term (this check against the check before it), rating and reviews gained, replies posted, the titles of what was published, directory counts and the name, address and phone check; the facts are frozen into the report row when it is made (`seo_reports`, status `collecting`). Claude writes a summary (600 characters at most), one recommendation (300) and exactly three priorities (120 each); an answer with a link, an address, a price, markdown or a promise ("guarantee", "number one", "first page", "will rank") is refused and the task stays claimed. A task nobody picks up in 14 days leaves the report with the sentence the code writes from the numbers (`source: plain`, no priorities) and its approval says so. A ready report gets ONE `seo.report` approval; approving it sends a fixed-template mail from the main mailbox (greeting, Claude's summary, the link, a sign-off), marks the report `sent`, writes one timeline line and ticks SEO-1's 1.7. Approving again sends nothing. A billing hold, a link base that is not usable, a mailbox that cannot send and a contact with no email make the approval go back to pending. A test report goes to your contact email only, with "[Test] " on the subject.

The client's page. `<CLIENT_LINK_BASE>/l/<token>` (public route `GET /api/public/l/:token`, read only, rate limited, `no-store`, noindex). Only a `sent` report is shown; an unknown, malformed, not-yet-sent, revoked or cancelled link is the same 404. The page is built field by field from the frozen facts and holds no place id, map link, review text, reviewer name or token. Each view is counted, except your own with your session. Your side: `/seo` (the board: one row per active client with what to do next), the client's Local SEO panel, `GET /api/seo/reports` and `PUT /api/seo/reports/:id` (your edit of the words, same rules as Claude's, rewrites the pending approval's card), `POST /api/seo/reports/:id/revoke`, and the read-only MCP tool `get_seo_status` (never a link, a token, a place id or review text; a rehearsal client is left out).

End-to-end test. `test/seo-flow.test.ts` drives the real entry points on a fixed calendar (Los Angeles): the owner's routes under `/api` with a real session, the daily cron on Tuesday 1 December 2026 at 09:00 and on three later days, Claude's words through the queue's own completion (the function and the MCP route, with a refusal each for a reply with a link, a Google post with meta text, and a report summary with "guarantee"), the queue's own expiry on 17 December, the real approval path, the public route and the MCP route. The only fakes are Google Places and the clients' own websites (the Worker's fetch, one small router that answers by URL and field mask: text search with a richer mask is the candidate search, with the mask `places.id` it is the ranking search, details by URL), Stripe's read of an open invoice (the billing sweep asks about the held client's invoice once it is a day old), the registry lookup the daily cron makes, and the mail transport. The story: Ace Plumbing (Local SEO, two terms, a place with 40 reviews, set up through the routes on 27 October with two same-name businesses in the place search), Bravo Heating (Growth, whose places sub-cap is reached by Ace's calls so it gets no Places call that day and still a report from its baseline), a client on billing hold and a test client (both with an active profile, terms and a monthly cycle, so only the rules keep them out). Ace's SEO-0 is finished through the route and attaches the cycles; October and November's history (the baseline, a check and snapshot of 2 November, a page published in November, a review whose reply was posted) is written as data because no entry point replays a month. On 1 December the cron reads Ace's listing (three new reviews, one of 2 stars that tries to give Claude an order), pulls 18 grid points, makes 3 and 6 slots with their draft tasks, ticks 1.1 and starts both reports; a second run changes nothing and asks Google nothing. Then Claude's words, drafts edited, approved and posted, the report approved (once and again), the one mail with only Ace's link, the public page (the grid, the gains, the published title, the three priorities, a view counted; the owner's own opening is not), the 404 cases, the MCP answer, a rehearsal report that mails only you, a take-back (404 at once), Bravo's words never written and expired on 17 December into the code's own summary (approved, mailed, opened, taken back), and 1 January: January's slots and ticks and the December reports with the replies posted, the page published and movement against 1 December. At the end every public body, mail, MCP answer, approval card and what Claude was shown has no Google place id, map address, key, review text, reviewer name, guarantee word or report token but the client's own link in its own mail, every number is finite, and nothing was logged as an error but the spend cap's one line per run. The flow test found **two defects** in the code it exercises (R1 and R2 below), each fixed with its own test.

## Rulings made while building

Each is plain: what, and what it costs.

Found by the flow test (the flow test's own fixes).
- R1. Content drafts that nobody wrote stayed stuck for good. A draft task nobody picks up in 14 days expires, and its slot goes back to `planned` with no task, "so the next sweep queues it again". The daily sweep only looked at a month whose slot rows were fewer than the plan, so a slot that was `planned` with no task was never looked at again: Bravo's six December drafts would have shown "Claude has not drafted this yet" for ever. Fixed in `src/worker/seo/sweep.ts`: a month with a `planned` slot that has no task is due too, and the same sweep hands it to Claude again; a unit test in `test/seo-sweep.test.ts` (an expired slot is queued once, the drafted one is left alone). It also heals a crash that came between making a slot row and queueing its task. The re-queue is capped by R9 below.
- R2. The "N reviews we cannot see" flag was never shown. `watchReviews` worked out how many reviews the listing gained that Google did not show us and the daily sweep threw the number away, so call 4 of the plan was not true. Fixed in `src/worker/seo/sweep.ts`: the sweep writes one line on the client's timeline per watch ("Local SEO watch <date>: the Google listing has N more reviews than Google shows us. Check the profile."); a unit test in `test/seo-sweep.test.ts`, and the flow test checks it on 1 January. Costs: it is a timeline line, not a Today row.
- Not a defect, and no ruling (what the flow test had to learn about the app, in case you rehearse by hand): starting a client's project seeds its site from the lead's website address, so a client's site address must be set on the lead as well as on the site, or the name, address and phone check reads the old address; the billing sweep asks Stripe about an open invoice a day after it was sent, so a flow test that runs a cron weeks later must answer that read; the cap's logged line is an error-level log by design (one per run, `seo sweep: the Places spend cap is reached, so the watch and the rank pulls wait`), so the flow test allows exactly that line and nothing else.

Found by the final whole-branch review (fix wave, one commit each, each with its own test).
- R3. The name, address and phone check told the client things it never measured. A listing with no phone made any phone on the site a "mismatch", and an address like "Portland, OR" (a service-area business) made the address "missing", and both reached the client's summary. A fourth value, `unknown` ("nothing to compare"), is now returned for a phone, an address key or a name the listing does not have; the client's summary and page leave it out (the summary says only what matched), Claude's brief says "not compared" and the owner's panel says so. Costs nothing; old stored results still read.
- R4. A first report claimed an improvement: "This is the first check, so nothing to compare yet" followed by "It gained 3 reviews since the previous check". With no earlier rank check the report's review gain is now null, so no summary sentence, approval line or page row says it. A report with an earlier check still shows it. Costs: the first report after a baseline shows the rating and the count but no gain.
- R5. A Google place id that stopped resolving, or changed, was silent: the watch returned quietly, never set the watch day (so the paid details call repeated daily) and, if Google had moved the listing, every grid point read "not in the top 20". Both cases now pause the client with one timeline line (see the sweep paragraph above); picking the place again and the baseline re-activate it. Costs: the client stops getting reports until you pick the place again.
- R6. A rehearsal report could never be mailed unless the test client had a finished SEO-0 (the flow test only passed because it wrote an SEO-1 cycle as data). The live-project check now applies to a real report only.
- R7. The Places budget. The first budget (700 calls against "1000 subrequests") rested on a limit a Paid Worker does not have: it is 10,000 subrequests, every D1 call counts, and a Places call is two (the request and its usage row). What binds a scheduled run is its wall time (about 15 minutes, calls one after another). The budget is now 400 calls (four clients with ten terms) AND a guard that starts no client's Places work 6 minutes after the sweep began (`MAX_PLACES_WALL_MS`); reports, slots and ticks are never held by either; the clients not reached go first the next run. Costs: a busy morning pulls some clients a day late.
- R8. A key Google refuses (401 or 403) fired up to 90 failing calls per client per day. A rank run now stops at the first 401 or 403 (like after three throttled calls in a row), stores the day's check as not checked, and the sweep does not try that client again that day.
- R9. The content re-queue (R1) had no limit: a task Claude failed every day made a new task every day. A slot is now handed over again only until two draft tasks for it have ended failed or expired; after that it stays `planned` for you, and the panel says "Claude could not draft this: write it yourself or reject it." (the content answers carry `draftTries` for this). Costs: a slot Claude cannot draft twice is yours.
- R10. A reply with "feel free to call us" or "hassle-free" was refused because the word "free" was on the offer list. The list now names offers of free work (free of charge, service, repair, estimate, quote or work; for free; complimentary; no charge).
- R11. A review reply task's expiry was not filtered by task id as its failure is, so an old task's late expiry could send a newer task's reviews back to `new`. The queue now hands the expired task to the kind's `onExpire` hook and the reply kind only releases reviews that task was drafting.
- R12. The report's promise list missed "will improve" and its kin; it now refuses "will" followed by improve, increase, rise, climb, grow or get, in Claude's words and in yours (one shared validator).
- R13. The client's page said "no grids to show" and drew grids of "not checked" when there was no rank check. It now draws none.
- R14. `README.md` said 29 tools, left out `get_seo_status`, and said Local SEO had no SOP; fixed.

## Known gaps (decided, not fixed)

Never run for real
- No real Google call, mail or page was ever run; the Places answer shapes in the tests are from Google's documentation. The rank is an approximation of Maps (above).
- The flow test pins only `Date`, so real timers are real. History (October and November) is written as data, so a real month of daily crons, the weekly watch and a month of drift between checks are not exercised end to end. The owner pages are not exercised in a browser by any test, and no component has a behaviour test (the repo is node-only).

Places and the grid
- The grid is 9 ids-only calls per term, sequential, inline in the manual baseline and rank-check routes: a baseline of ten terms is 90 calls in one request and may take a minute.
- A term added mid-month is not pulled until next month's pull (or your rank-check button). A point's search radius is not clamped to Google's 50 000 metre limit (the largest grid is 5 000).
- A client costing more than the 400-call budget alone would halt all Places work (cannot happen at ten terms: 91 calls). A retry re-runs all of a client's terms, including those that were already usable (the cost bound above covers it). The 6 minute guard is read from the clock, so a single Places call that hangs for its own timeout can still run past it by that timeout.
- A re-pull on a later day after a throttled first day may leave a term out of that month's report: the report is frozen on the first day ANY term has a usable check.
- A failed re-read of the checks after a pull falls back to the checks from before it, for that day only.

Profile, keywords and the name, address and phone check
- The keyword cap of ten has a race (list, then insert): two quick adds could pass it. `siteId` cannot be cleared by `PUT profile`. The address check is the street number and street name both present on a page, not their adjacency. Lower-casing a page with some Unicode letters can shift an index (rare). `upsertRankCheck` does not check that the keyword belongs to the business (callers iterate the business's own terms).
- The baseline switches the watch on and logs its line even when the grid measured nothing (it says `ranked: 0`).

Reviews
- A reply is not checked for markers such as two blank lines with spaces between them.
- On a second watch the same day the "cannot see" count can over-report.

Content
- A content draft may hold a link (only scripts, phone numbers, emails, dollar amounts and ranking promises are refused); a Google post with a link is allowed.  The content promise list misses "number 1", "page one of Google" and "best plumber in Portland" and refuses the honest "can't guarantee results".
- Rejecting a slot and its timeline note are two statements, so a failure between them leaves a rejection with no note. A slot rejected between queueing and marking leaves a pending task nobody needs (harmless).
- A content slot whose draft failed or expired twice is left `planned` for you (R9): it is not handed to Claude again, so write it or reject it.

The report
- The date of the check is the earliest across terms. The word list for promises in the report's words is a substring match ("compromise"); forward-looking phrases are caught only for "will" followed by improve, increase, rise, climb, grow or get.
- The card writes the date as "December 1" and the page as "1 Dec". `ratingChange` is in the public JSON and never drawn; exact positions are in the public JSON though the page shows bands (1 to 3, 4 to 10, 11 to 20).
- A real send checks for a live SEO-1 project, not a live subscription. `proposeSeoReportApproval` throws for a report that is not ready and has no approval (the Care one returns null). A revoked or cancelled report cannot be rebuilt in this version: there is one report per client per month, and nothing in the app can replace it (same as Care).
- The plain-summary report must be given a recommendation and three priorities before you can edit its words.

SOPs and the daily start
- The sweep's SQL names `local_seo`, `local_seo_growth` and `SEO-0` as text instead of using the constants. Some test names say "ten" steps where SEO-0 has nine. An inactive SEO-0 template is retried on every sweep turn. SEO-0 may start for a document that is already paid on the first cron (Needs Logan 5).

Your side
- The owner's reads are not bounded: the client's panel and the MCP tool read all of a client's rank checks and snapshots, and all reviews before keeping the newest 100. Fine for a year, bound them with a window before a client has several years.
- The board lists only clients whose profile is `active`, while Today shows drafts for any real client. Marking a Today row "done" hides a new draft row for the whole window. The panel's "previous" check is the one before the latest, the report's is the last usable one before, so the panel may say "not comparable" where the report compares. The board's "Build report now" is offered only when there is no report (the panel also lets you build after a revoke, which returns the revoked row). A review draft can stay marked unsaved after you save trailing spaces. The inserted "Say" line is announced politely and some sections have nested aria labels.
- `test/mcp-leaks.test.ts` calls the SEO tool without any SEO data, so that case is a no-op assurance (the flow test does check the MCP answer against sentinels).
- Pre-existing and not this plan's: a CSS class (`.rp-bar` in `clients.css`) collides so the "For <client>" header on the Care report, Proposal, Change order and Report public pages is squashed. It needs a one-line rename as its own change.

Tests
- The same known flakes as before, each passing alone: `billing-flow`, `billing-sweep`, `projects-flow` (timing under full-suite load), `sites-onboarding-items` (fails when a random UUID contains "abc"), `sites-seed`, `care-reports-flow` under load, and the MCP rate-limit test beside other MCP tests.

## Rollback
The Worker can be rolled back safely onto the new schema once the migrations are applied: the code from before this plan ignores the seven new tables and has no `/l/` page. The schema itself is rolled back only through the D1 Time Travel bookmark recorded before migrating (Needs Logan, item 1). A report already mailed stays in the client's inbox, but its link stops working while the old Worker is live, and works again when the new Worker is back. The SEO-0 projects the first cron makes for already-paid clients stay after a rollback.
