What was built, in seven parts.

The month's numbers. A daily rollup (`src/worker/monitoring/rollup.ts`) copies each site's checks into `site_uptime_days`, one row per site per local day (booking zone), because the raw checks are deleted after 35 days. The daily cron recomputes today and the three days before it, so the last day of a month is settled on the 1st. A day counts as covered from 144 checks (half a normal day); the percent is ok checks over all checks of the covered days, to one decimal, and any failed check caps it at 99.9 (it never reads "100%" after an outage). The report facts (`src/worker/care/reportFacts.ts`) are frozen into the report row when it is made: per site uptime, days covered, "monitored since", incidents and the longest outage, updates applied, rolled back and failed (read from what each run recorded, not from the update's status now), backups, a mobile PageSpeed score (when the key answers), the edit hours, and the renewals due in the next 60 days (domain, certificate, subscription term end). A number that could not be measured is null and left out, never 0 or 100%. No plugin name, slug, incident sentence, backup file name, SSH alias, folder, vault item or access note is read into the facts.

The edit hours and edit requests. CARE-3 is a new seeded checklist (never started as a project). "Edit request" is one button (`POST /api/clients/:id/edit-requests`): it makes a non-billable task on the client's live Care project with CARE-3's five steps as its checklist, flagged `edit_request`. The ledger (`src/worker/care/ledger.ts`) adds up only the non-billable minutes logged on those tasks, by the month each entry started in (booking zone), against the allowance: Care 60 minutes, Care Plus 180, Care fallback 60. It warns at 80% and says `over` past the allowance; over the allowance shows the real figure and nothing is quoted or billed by itself. Today gets a `care_edit_hours` row (priority 60 from 80%, 64 when over) for the current month, and the client's Care panel shows the ledger.

The monthly start. The daily cron finds each Care client's CARE-4 task for the current month (made on the 1st) that is not done or skipped and, if the client has no report of the month before yet, builds it and stores it (`care_reports`, status `collecting`), queues a `care.report` job for Claude and ticks CARE-4's 1.1 and 1.4. Clients with a billing hold, test clients, a Care project that is not live, a Care subscription that is not live and a client whose Care began after the reported month get none. Nor does anyone get one for a month the uptime rollup has no day for: the sweep builds nothing until the rollup has written a day on or before the last day of the reported month, so the first sweep after the rollup ships builds nothing, and the first real report is for the first month the rollup covers at least partly, which will be thin. At most 50 are started per run; a failure of one client is logged and never stops the others. `POST /api/clients/:id/care-report` ("Build now") makes one by hand on any day. CARE-4 no longer dispatches a Claude job of its own for step 1.1 (the old dispatch did, and is now skipped).

Claude's words. The `care.report` task kind gives Claude the numbers in the untrusted block and asks for one summary (600 characters at most) and one recommendation (300 at most). An answer with a link, an email address, a dollar figure, markdown or a run of blank lines is refused and the task stays claimed. A task nobody picks up (expired after 14 days) or that is given up on leaves the report with the sentence the code writes from the numbers (`source: plain`), and the approval says so on its card.

The approval and the mail. A ready report gets ONE `care.report` approval (idempotent: a crash-retry returns the same one). Its card shows who it goes to, the subject, the mail as it will read, the recommendation and the headline numbers. Approving it sends a fixed-template mail from the main mailbox (greeting, Claude's summary, the link, a sign-off; no figure of its own), marks the report `sent`, writes one timeline line, and ticks CARE-4's 1.2 and 1.3. Approving it again sends nothing. A billing hold, a link address that is not usable, a mailbox that cannot send, a contact with no email and a blocked address make the approval go back to pending (approve it again once fixed). A report that is no longer ready, or a client whose Care ended, is closed with a plain sentence on the timeline. A test report goes to your contact email only, with "[Test] " on the subject. `care.report` cannot be proposed by an agent and cannot be bulk-approved.

The client's page. `<CLIENT_LINK_BASE>/m/<token>` (public route `GET /api/public/m/:token`, read only, rate limited, `no-store`, noindex). Only a `sent` report is shown; an unknown, malformed, not-yet-sent, revoked or cancelled link is the same 404. The page is built field by field from the frozen facts: domain, uptime, days checked, incidents, the longest outage, updates applied and rolled back, backups, speed, edit hours, renewals, the summary and the recommendation. Each view is counted.

Your side. `/care/reports` (the month's reports with status, the words to edit while a report is ready, the link to copy, Revoke, and a "Build now" list of Care clients with no report yet), `GET /api/care/reports`, `PUT /api/care/reports/:id` (your edit of the words: same text rules as Claude's, it rewrites the pending approval's card so you approve what the card shows), `POST /api/care/reports/:id/revoke` (the link stops working, the queued Claude job is closed and the pending approval is rejected), `GET /api/clients/:id/edit-ledger`, an "Edit hours" block with the edit-request button on the client's Care panel, and the read-only MCP tool `get_care_report` (a month's reports with status, words, headline numbers and edit hours; never a link or a token; the rehearsal client's report is left out).

End-to-end test. `test/care-reports-flow.test.ts` drives the real entry points on a fixed calendar (Los Angeles): the owner's routes under `/api` with a real session (the edit request, time logged on it, completing it, the ledger, Today, "Build now", the take-back), the daily cron on Wednesday 2 December 2026 at 09:00 (it rolls up 29 and 30 November from raw checks, makes each CARE-4 task and starts the reports), Claude's words through the queue's completion (the function for A, the MCP route for C, a link refused then a good answer), the queue's own expiry on the daily cron of 17 December (for B), the real approval path, the public route and the MCP route. The only fakes are PageSpeed (the Worker's fetch), the registry lookup the daily cron makes and the mail transport; November's history (uptime days, an outage, three update runs) is written as data because no entry point replays a month. The story: three Care clients (A with two sites, an outage of three hours on the 14th, two clean runs and one rolled back, 75 minutes of edit time over a 60-minute allowance, a certificate 40 days out; B monitored since 20 November with 30 minutes; C on Care Plus with no checks), a client on billing hold and a test client. The 2 December cron makes exactly three reports and three Claude tasks and ticks 1.1 and 1.4 for the three, and makes nothing for the held and test clients. ## Final review

The whole-branch review's nine findings, ruled and fixed in one wave (R12 onwards); each has its own test.
- R12. (Important 1) The daily sweep built a report for a month the uptime rollup never covered: deployed mid-November, the first cron would have built October for every client whose cadence was attached before 1 November, showing "No downtime recorded" and "No updates were applied" for a month nobody measured. `candidates` now requires the rollup's first day (`MIN(day)` of `site_uptime_days`, none at all means skip) to be on or before the last day of the reported month. "Build now" (`startReport`) stays unguarded on purpose. Costs: the first sweep after deploy builds nothing, and the first real report is a month later and thin (Needs Logan 8).
- R13. (Important 2) Unmeasured numbers are no longer shown as zero. A site with no covered day says "Not measured this month" on the downtime row (an outage is still shown). A new optional `updatesTracked` on each site's facts (true when an update run of the site finished in the month; missing reads as false, so stored reports still parse) decides whether the Updates row, the plain summary's update and backup sentences, Claude's update and backup lines, and the approval card's update and backup parts are shown. The public JSON and the MCP answer carry the flag, so the public site object has one more key. Costs: a site the weekly batch never touches has no update line at all, even if you update it by hand.
- R14. (Important 3) An update put back only because another one failed (`COLLATERAL_NOTE`, now exported from `src/worker/care/updateKind.ts`) is counted as neither rolled back nor failed. The client page no longer says "N undone because they caused a problem" for those. Costs: the facts module now imports `updateKind.ts` (and what it imports).
- R15. (Important 4) The owner's own visit does not count as a view: `GET /api/public/m/:token` skips `recordView` when the request carries a valid owner session cookie, like the events beacon. Costs: it works only when `CLIENT_LINK_BASE` shares the session cookie's site; a signed-out phone still counts.
- R16. (Minor 5) An outage that began before the month and ended inside it (or is still open) is in the month: incidents are the ones that overlap it, with the start cut at the month's first instant. An outage spanning two months is an incident of both. Costs nothing.
- R17. (Minor 6) The report's approval is drafted by `job`, not `logan`, so the card no longer says "Drafted by you". Costs nothing.
- R18. (Minor 7) Ruling: document only. A revoked or cancelled report cannot be rebuilt in this version (known gaps).
- R19. (Minor 8) The monthly reports are the last part of the daily run, so up to 50 clients waiting on PageSpeed one after another cannot starve the update batch, the backstop or the certificate check on the 1st. The cap stays 50 and logs `care reports: 50 clients started, the rest wait for the next run` when it is hit. Costs: the reports start after the other parts.
- R20. (Minor 9) This note: remote state is not claimed anywhere, and the corrections above are made.

## Known gaps (decided, not fixed)

Never run for real
- Nothing here has met the real Worker, mailbox or PageSpeed. The first real run is the rehearsal in Needs Logan.
- The PageSpeed fixture used in the tests is the hand-written one from Plan 3; the real answer may differ.

Uptime and the rollup
- No backfill: the rollup recomputes only the last three days, so the first report after deploy is thin (Needs Logan, item 8).
- The rollup reads five days of raw checks in one query and writes the days one at a time. Fine now; batch it before several hundred sites.
- The probe checks at most 40 sites per five-minute tick. Above about 80 monitored sites a site gets fewer than 144 checks a day and its uptime is left out.
- A change of booking zone leaves old rows in the old zone. The 2027-11-07 clock change is not tested (the 2026-11-01 one is); the count clamp is untested. `upsertUptimeDay` does not check that ok is at most the total (the rollup guarantees it).
- A rollup failure is logged and freezes that day's facts with the last day missing.

Edit hours and Today
- Marking Today's `care_edit_hours` row "done" hides it for 7 days with no "since", so it can hide a later `over` or the next month's row.
- No clock-change-day test in `test/care-ledger.test.ts`. `EDIT_ALLOWANCE_MINUTES` is a plain mutable constant. With several live Care subscriptions the most generous allowance wins. Today now reads every live Care client's ledger.

Report facts and what they say
- Uptime and incidents come from different sources (the rollup and the incident list), so a report can say 100% up and one incident; Claude's instructions say never to write "no problems" when incidents is above 0.
- A site with five covered days and a start date in the month shows its percent without a partial-month note on the page; the plain summary does say "checked from <date>".
- The speed sentence of the code-written summary lists only the first three sites as if complete.
- The facts schema is loose: no hostname or date check beyond a pattern, and null uptime is not tied to zero days covered.
- A renewal that has already passed leaves the list silently. `annual_renewal` is in the schema and never made (no data source).
- Step ids are not checked against the job's payload. The counts depend on `helper_jobs.result` never being pruned.

Claude's summary
- `propose()` swallows a null from `proposeReportApproval` (it never returns null for a ready report now). The "stale" reason for a cancelled report reads misleadingly. No test makes `propose` throw. `build()` can throw if the proposal throws (the task stays claimed and recovers when its lease runs out). A sentence that starts with "#1" is refused as a heading.

CARE-4 and the daily start
- 1.4 is ticked when the facts are built and over-claims against its own "done when" (failed charges, cards about to expire and annual renewals have no data source). Reword 1.4 or tick it by hand. Step 1.1's text also still promises security, traffic and search highlights.
- The CARE-4 task shows on the open-task lists as pending Claude work all month (it is never dispatched; 1.5 and 1.6 are yours, so it only completes when you tick them).
- A permanently failing client could starve others at the 50-per-run cap (the cap now logs one fixed line when it is hit). Two log-order assertions in the sweep test pass trivially.
- A revoked or cancelled report cannot be rebuilt in this version: there is one report per client per month (`UNIQUE(business_id, period)`), and "Build now" returns the revoked row. Nothing in the app can replace it; if you take back a ready report and want another for that month, ask for a follow-up (a new row, or reopening the old one).

Approval and mail
- The `sendEmail` row stuck in "sending" edge is shared with every other kind of mail.
- The mail for a retry after a crash can log "not ticked" for a real report whose 1.2 and 1.3 were already ticked (a harmless repeat).

The client's page
- A signed-out opening of the link by you (a phone that is not signed in, or an address that does not share the session cookie's site) still counts as a client view.
- The footer text contrast is about 3:1 (use `--text-2`). The noindex header is on the API answer only; the page shell has the meta tag. "1 h 35 min" wraps on a narrow phone. `Math.round` in `src/client/careReportPageView.ts` can show 99.996 as 100% (the facts already cap at 99.9, so the risk is low).

Your side
- Editing the words and rewriting the card are two statements, so for a moment the card shows the old words (the mail reads the live row). `cancelReport` has no production caller (it is there for a future one). The edit route accepts an empty recommendation (the code-written summary has none). A ready report's page shows "link" that is a 404 until it is sent (it should say "works once sent"). "Build now" is offered only for real clients with no report, never for a test client. The link box id comes from the token's tail.
- `setSummary` sets status `ready` for any `from` it is given: callers must pass only `collecting` or `ready`, never `sent` or `revoked` (the two callers do).

Tests

## Rollback

A report already mailed stays in the client's inbox, but its link stops working while the old Worker (which has no `/m/` page or route) is live, and works again when the new Worker is back.
